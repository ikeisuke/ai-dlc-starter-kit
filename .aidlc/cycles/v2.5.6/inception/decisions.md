# 意思決定記録 - v2.5.6

## DR-001: サイクルスコープを 4 項目（A/B/C/D）すべて含める

- **ステップ**: Inception Phase / Step 03 (Intent 明確化) / Q3 トレードオフ確認
- **日時**: 2026-05-09

### 背景

v2.5.5 リリース時に浮上した残務 4 件（A: CI ガード / B: fixture 除外 / C: permissions audit / D: AskUserQuestion 単一/複数選択ポリシー）について、patch サイクル v2.5.6 の現実的なスコープを決定する必要があった。AI からは初期推奨として「長期課題は除外し、現状ギャップの埋め込みのみ」が提示されていた。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | 長期課題は除外、現状ギャップの埋め込みのみ（A/B/C のスコープを狭く） | サイクル工数の確実な収束、レビュー負荷低減 | 実装側ツール化や CI ガードの完成度が不十分なまま残る |
| 2 | A も D も広げて含める（A: ローカル実行スクリプト・ヘルプまで、D: 検出スキル・lint 追加まで） | 残務を一掃、後続サイクルでの再着手を回避 | サイクル工数増、Construction Phase の Unit 並列度が増える |

### 決定

**選択肢 2** を採用（ユーザー指示「全部含める」による上書き）

### トレードオフと判断根拠

- **得たもの**: 4 項目すべての完成度を本サイクルで担保し、残務の繰り越しを最小化。CI ガードはツール化（ローカル実行スクリプト + ヘルプ）まで含め、開発者体験を底上げ
- **犠牲にしたもの**: サイクル工数の増加、Construction Phase で 4 Unit を並列管理する複雑さ
- **判断根拠**: ユーザー（メンテナ）が「全部含める」を明示選択。依存関係なし（やりやすい順で良い）の方針もあり、Unit 並列管理の負荷は許容範囲。各 Unit の見積もりは小〜中の範囲で、1 サイクルでの完結が現実的

## DR-002: Intent 成功基準 A の暫定完了条件設定

- **ステップ**: Inception Phase / Step 03 (Intent 明確化) / AI レビュー Round 2 対応
- **日時**: 2026-05-09

### 背景

A (CI ガード) の DoD には A-1（コード/CI 実装）と A-2（GitHub Repository Ruleset / Branch protection 適用）が含まれる。A-2 は `gh api` でスクリプト化できる場合は自動だが、UI 手動作業のみ可能な場合はリポジトリ管理者の操作待ちとなる。本サイクル中に管理者適用が間に合わない場合の取り扱いを決定する必要があった。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | A-2 を必須として、未適用なら A 全体を未達扱い（v2.5.7 へ持ち越し） | 一貫性・厳格性・成功条件の明確さ | 管理者の操作タイミングに依存、リリース全体がブロックされる |
| 2 | A-2 暫定完了条件を設け、A-1 完了 + ユーザー明示承認 + follow-up Issue 起票で A 達成とみなす | 現実的・運用柔軟・コードリリースは進められる | 完了判定が二段階化、運用ルールが複雑化 |

### 決定

**選択肢 2** を採用

### トレードオフと判断根拠

- **得たもの**: コード実装が完了していれば管理者作業未完了でも本サイクルをリリースできる柔軟性。実害（CI ガード未必須化）は follow-up Issue で必ず追跡される
- **犠牲にしたもの**: 完了判定の二段階化（通常 / 暫定）、運用ルールの追加学習コスト
- **判断根拠**: メタ開発リポジトリの実態として、Repository Ruleset 適用は GitHub UI 操作が必要になりやすく、開発者と適用者が分離するケースもある。コードレベルの達成（A-1）と管理設定の達成（A-2）を分離し、暫定条件には明示的承認 (`AskUserQuestion`) を必須化することで運用ガードを担保

## DR-003: C の HIGH/CRITICAL 対処方針 (ask 必須、acknowledged 不可)

- **ステップ**: Inception Phase / Step 04 (Unit 定義) / AI レビュー Round 1 対応
- **日時**: 2026-05-09

### 背景

C (permissions audit 解消) の対処方針として、検出 9 件（CRITICAL 1 / HIGH 1 / MED 7）に対する acknowledgedFindings 登録と ask 追加の使い分けを決定する必要があった。Intent 段階では「すべて acknowledged 登録または ask 追加で対処」と緩く記述していたが、Unit 定義レビューで HIGH/CRITICAL の扱いに齟齬が指摘された。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | HIGH/CRITICAL を acknowledged で抑制可とする | 実装シンプル、ユーザー操作不要 | 危険な拡張サブコマンドが透明化され、事故防止効果が薄い |
| 2 | HIGH/CRITICAL は ask 追加で対処必須（acknowledged 不可）、MED は ask または acknowledged のいずれか可 | 危険操作で 1 段階確認が入り事故防止効果が高い、severity に応じた合理的差別化 | ask 追加によりユーザー操作が 1 段階増える |

### 決定

**選択肢 2** を採用

### トレードオフと判断根拠

- **得たもど**: severity に応じた合理的な対処方針。HIGH/CRITICAL の透明な抑制を防ぎ、危険な拡張サブコマンド（`--force`, `-d` 等）には必ず確認を挟む安全性
- **犠牲にしたもの**: ask 追加によるユーザー操作 1 段階増。ただし日常操作（`git push *`, `git tag *` 自体は許可）は影響なし、`--force` / `-d` 等の拡張形のみ ask 化
- **判断根拠**: パーミッション衛生は信頼できる仕組みで自動化すべき（acknowledged は note を残せるが事故防止には弱い）。HIGH/CRITICAL は本来「危険」の signal なので、note で済ませるのではなく確認フロー導入が合理的
