## DR-001: サイクルバージョンを v3.0.0-alpha.7（Phase 6）とする

- **ステップ**: セットアップ（サイクルバージョン決定）
- **日時**: 2026-06-28

### 背景

現ブランチ名が `v3.0.0` で、`suggest-version.sh` は prerelease を無視して `v3.0.0`（major）を提案していた。一方 Epic #736 ロードマップ上、Phase 5（alpha.6）の次は Phase 6 = v3.0.0-alpha.7。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | v3.0.0-alpha.7（Phase 6） | ロードマップ通り。reflect+doctor で v3 単独フルサイクル完走へ | 本流化(Phase 7)はまだ先 |
| 2 | v3.0.0（最終 / Phase 7 着手） | 本番リリースへ前進 | Phase 6 未了で前提が崩れる |
| 3 | 別バージョン指定 | 柔軟 | ロードマップとの整合が崩れる |

### 決定

**v3.0.0-alpha.7（Phase 6）** を採用。

### トレードオフと判断根拠

- **得たもの**: Epic #736 ロードマップとの整合。Phase 6 完了で「v3 をスキルとして使える」状態に到達。
- **犠牲にしたもの**: v3.0.0 GA への直接前進は一旦見送り。
- **判断根拠**: Phase 6（reflect+doctor）未了のまま Phase 7（本流化）に進むと「v3 単独フルサイクル完走」の前提が崩れるため、ロードマップ順を維持。

## DR-003: doctor を 7（+pr）領域 shallow + parse-guard とし、phase/trace を alpha.8 へ defer

- **ステップ**: Intent 明確化（doctor 診断スコープ）
- **日時**: 2026-06-28

### 背景

renewal-plan の doctor は config/state/cycle/work-items/git/gh/pr/scripts/phase/trace を診断する設計。実測で `[phase]` 導出 code 化（~100行）・`[trace]` 整合（~200行）が実装負荷の大半を占め、機能確定待ちと判明。ユーザーから「やり過ぎ注意」の指示。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | 7(+pr)領域 shallow + parse-guard（phase/trace defer） | 既存スクリプト再利用で軽量。Phase 6 完了条件を満たす | doctor 全項目は alpha.8 へ持ち越し |
| 2 | phase も含める（8領域） | より網羅的 | phase 導出 code 化でやや重い |
| 3 | フル6+領域（phase+trace） | renewal-plan 通り | trace 整合で 1 サイクルには重い |

### 決定

**7(+pr)領域 shallow + parse-guard（phase/trace は alpha.8 defer）** を採用。AIレビュー指摘を受け、defer を SoT（workflow.md §3.6 / renewal-plan / Epic #736）へ明示反映する作業をスコープに追加。

### トレードオフと判断根拠

- **得たもの**: 軽量で読める doctor v1。既存スクリプト再利用。Phase 6 完了条件「v3 単独フルサイクル完走可能」は充足。
- **犠牲にしたもの**: doctor の phase/trace 診断は alpha.8 へ持ち越し。
- **判断根拠**: 実装負荷の大半を占める phase/trace を切り出し、完了判定の二重化は SoT 反映で防ぐ。やり過ぎを避けつつ完了条件を満たす最小構成。

## DR-004: #735（squash-unit.sh）の修正方針は段落結合（git 準拠）

- **ステップ**: Intent 明確化（#735 修正方針）
- **日時**: 2026-06-28

### 背景

`squash-unit.sh` の複数 `--message` 指定で subject が失われる footgun。Issue #735 が 3 つの改善案（段落結合 / エラー化 / --message-file 統一）を提示。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | 段落結合（git 準拠） | git commit の慣習と一致。最も人間工学的 | 実装はやや複雑 |
| 2 | 明示エラー化 | 最小実装 | 呼び出し側修正が必要 |
| 3 | --message-file 統一 | file-based 推奨と整合 | 既存呼び出しの移行が必要 |

### 決定

**段落結合（git 準拠 / 1 個目=subject、以降=本文段落）** を採用。

### トレードオフと判断根拠

- **得たもの**: AI エージェント・利用者が `git commit` の慣習どおり複数 `--message` を安全に使える。
- **犠牲にしたもの**: エラー化より実装がやや複雑。
- **判断根拠**: footgun の根本は「複数 --message 未サポート」。エラー化は回避に留まり、段落結合は本来期待される挙動を実現する。AI エージェントの習熟コストが最も低い。
