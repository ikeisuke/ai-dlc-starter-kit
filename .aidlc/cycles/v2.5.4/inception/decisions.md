## DR-001: patch スコープ保護のため Unit 004 の修正対象を 1 ファイル限定とする

**決定日**: 2026-05-07

### 背景

Unit 004 は v2.5.3 リリース直後に判明した `predecessor-issue.sh` の zsh source 互換性問題を解決するためのもの。当初、helper 6 ファイル全てを「修正対象 + テスト追加対象」とする案があったが、Codex review Round 1 で「patch スコープが膨らむリスク」を指摘された。

### 選択肢

1. **全 helper 6 ファイルを修正 + テスト追加**: スコープが大きく、patch リリースとして不適切
2. **必須修正対象 1 ファイル + 全 helper テスト追加（採用）**: 実害発生済みの `predecessor-issue.sh` のみ修正し、他 5 ファイルはテストで動作確認のみ。テスト失敗時は OUT_OF_SCOPE として次サイクル候補
3. **修正対象 1 ファイル + 同ファイルのみテスト追加**: テストカバレッジが不十分

### 決定

選択肢 2 を採用。**修正対象は `predecessor-issue.sh` の 1 ファイルに限定**し、他 5 ファイル（`aidlc-paths.sh` / `aidlc-validate.sh` / `aidlc-gh.sh` / `aidlc-spool.sh` / `retrospective-issue.sh`）は zsh source 動作確認テストの追加のみで構造変更しない。テスト失敗時は OUT_OF_SCOPE として次サイクル候補とする。

### 根拠

- patch リリースとして妥当な規模を保つ
- 実害発生済みファイル（`predecessor-issue.sh`）の修正で v2.5.3 由来のリスクは解消
- 他 5 ファイルのテスト追加で zsh 互換性問題の有無を可視化し、次サイクルでの優先度判断材料を確保

## DR-002: Unit 003 設計レビュー早期 defer ガイドを Construction Phase 限定に絞る

**決定日**: 2026-05-07

### 背景

Unit 003 は `steps/common/review-flow.md` に設計レビュー特化の早期 defer ガイドを追記する。`review-flow.md` は共通手順ファイル（Inception / Construction / Operations 全フェーズで参照）であるため、追記内容が他フェーズのレビューにも適用されると意図しない副作用が発生する懸念があった。

### 選択肢

1. **全フェーズのレビューに適用**: Inception / Operations のレビューでも閾値が適用され副作用が広範囲
2. **Construction Phase の設計レビュー限定（採用）**: 設計仮説の議論密度・後半での仮説追加・個別点漸進パターンが顕在化するのは設計レビュー特有のため、限定が妥当
3. **Construction Phase 全レビュー（設計 + コード + 統合）に適用**: 設計レビュー以外のレビューには議論密度の概念が適用しづらい

### 決定

選択肢 2 を採用。Unit 003 の境界に「Inception / Operations Phase のレビューには適用しない」を明示し、追記サブセクション冒頭に「適用範囲: Construction Phase の設計レビュー（ドメインモデル / 論理設計）に限定」を明記する。

### 根拠

- 設計レビュー特化の議論密度・新規仮説追加検出は他フェーズのレビューに転用しづらい
- 共通手順ファイル内で適用範囲を明示することで、他フェーズのレビュー実装に影響を与えない
- 拡大適用は次サイクル以降の OUT_OF_SCOPE 候補として残す

## DR-003: Unit 001 ステップ7「完了」更新タイミングを §7.7 Git コミット時に確定

**決定日**: 2026-05-07

### 背景

v2.5.3 サイクルで AI が PR マージ後に `progress.md` のステップ7状態を更新し、マージ前完結契約違反を起こした。修正候補は 3 つあった: §7.7 Git コミット時 / §7.8 PR Ready 化時 / §7.12 PR マージ前レビュー完了時。

### 選択肢

1. **§7.7 Git コミット時に「完了」更新（採用）**: progress.md の固定スロット更新（§7.6）と同一コミットに含めることができ、マージ前完結契約と最も整合
2. **§7.8 PR Ready 化時に「完了」更新**: Ready 化は GitHub 側操作のため、ローカル progress.md と GitHub PR 状態の同期タイミングが分かれる
3. **§7.12 PR マージ前レビュー完了時に「完了」更新**: レビュー完了の判定タイミングが曖昧（複数 round の場合の終端判定が困難）

### 決定

選択肢 1 を採用。**§7.7 Git コミット時に progress.md ステップ7「完了」更新**を確定する。これにより、§7.6 progress.md 固定スロット更新（`release_gate_ready=true` / `completion_gate_ready=true`）と同一コミットに含まれる構造になり、マージ前完結契約と完全整合する。

### 根拠

- progress.md の更新がローカルファイルベースで完結し、GitHub 側操作と分離される
- §7.6 / §7.7 の既存サブステップに自然に組み込める
- §7.13 マージ後の追加編集が不要になり、マージ前完結契約違反が構造的に発生しない
