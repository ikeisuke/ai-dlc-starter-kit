## DR-001: サイクルバージョンの選択（patch / minor / major）

- **ステップ**: 01-setup ステップ8（バージョン提案）
- **日時**: 2026-05-07

### 背景

v2.5.2 振り返り（#651）で Try が複数件発生したため、v2.5.3（patch）/ v2.6.0（minor）/ v3.0.0（major）の 3 候補からサイクルバージョンを決定する必要があった。スコープを絞るか統合するかでバージョンが分かれる。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | v2.5.3 (patch) | スコープ絞込により納期最小化、後方互換維持が容易 | Try 全件は捌ききれない |
| 2 | v2.6.0 (minor) | Try 全件 + Feedback 統合可能 | スコープ広く納期増、設定キー追加など破壊変更可能性 |
| 3 | v3.0.0 (major) | 大規模リファクタ可能 | 今サイクル Try に該当せず過剰 |

### 決定

**v2.5.3 (patch)** を採用。

### トレードオフと判断根拠

- **得たもの**: 納期最小化、後方互換完全維持、スコープが「振り返り機能の信頼性向上」に集中
- **犠牲にしたもの**: Try のうち #621 mirror Issue 自動重複統合 / #644 retrospective-resend AIDLC_PROJECT_ROOT 対応など minor 級の改修は別サイクルへ繰越
- **判断根拠**: 個人設定のトレードオフスライダー（スコープ:大、予算:小、納期:最小、品質:最大）に従い、納期最小化を優先しつつスコープを 4 Unit に集中させた

## DR-003: 主目的の位置付け（振り返り信頼性 vs 個別バグ集約 vs ドキュメント明文化）

ユーザーが「振り返り機能のバグ修正、改善を中心にやりたい」と回答した後、4 件の Issue（#647/#637/#634/#643）の主目的をどう位置付けるかが、Intent の文脈・PRFAQ・Construction Phase での実装優先度に影響する。

| # | 選択肢 | メリット | デメリット |

## DR-004: #634 取り込み範囲の絞込み（事実テーブル抽出 + 推定値検出のみ）

- **日時**: 2026-05-07

### 背景

#634（振り返りプロセスの構造的改善）は原文で 5 項目の改善案を含み、v2.5.3 patch スコープに全部取り込むには規模が大きい。ユーザーが「634 で対応しないものは別 issue にしちゃって」と指示。

### 選択肢

| # | 選択肢 | メリット | デメリット |

| 1 | 事実テーブル抽出 + 推定値検出ガードのみ取り込み、3層検証 skill 化 / jsonl 解析 helper を別 Issue に切出し | patch スコープに収まる、最も影響度高い 2 項目を本サイクルで処理 | - |

- **判断根拠**: トレードオフスライダー（スコープ:大、納期:最小）に従い、最大インパクトの 2 項目に集中。残りは別 Issue として明文化することで継続性を担保（ユーザー明示指示）

## DR-006: 推定値検出ガードの許容条件を「根拠リンク併記」のみに固定

- **ステップ**: 03-intent / 04-stories-units（Intent Round 3 指摘 #2 対応）
- **日時**: 2026-05-07

### 背景

Intent Round 3 で「`一次情報 Read 済` の場合の挙動」と「数値+近似語で flag」のルールに自己矛盾の種があると指摘された。「一次情報があれば許容するのか / 根拠リンクがあれば許容するのか」を Intent で明文化する必要があった。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | 「根拠リンク併記」のみを許容条件とし、一次情報 Read の有無は flag 判定軸に使わない | flag 判定が機械的 / レビュー時の判定軸が一意 | 一次情報を Read していても根拠リンクなしの近似数値は flag される（軽い誤検知耐性低下） |
| 2 | 「一次情報 Read 済」も許容条件として追加 | 厳しすぎず実態を反映 | 「Read 済」を機械判定できず、運用上のチェック不能 |
| 3 | 「近似語付き数値は常に flag、許容条件なし」 | 完全な厳格化 | 過検知が多く、運用負荷増 |

### 決定

**「根拠リンク併記」のみを許容条件とする**（選択肢 1）。一次情報 Read の有無は flag 判定軸に使わない。

### トレードオフと判断根拠

- **得たもの**: flag 判定軸の一意化（誰がレビューしても同じ判定結果）、機械検証可能性
- **犠牲にしたもの**: 一次情報を Read 済みでも根拠リンクが省略された場合、軽い誤検知が発生する（ただし許容範囲）
- **判断根拠**: 「Read 済」は AI レビューワーから機械判定できないため、運用ルールとして根拠リンク併記を義務化することで判定の再現性と監査可能性を確保

## DR-007: review-flow 5R 上限超過時の指摘対応判断（Intent Round 5）

- **ステップ**: 03-intent ステップ1（Intent AIレビュー）
- **日時**: 2026-05-07

### 背景

Intent AI レビュー Round 5 で 1 件指摘（中: regex のエスケープミス）が発生し `decision_required` 状態になった。仕様上は「修正する」/「TECHNICAL_BLOCKER」/「OUT_OF_SCOPE」の 3 択。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | 修正する → 反復レビューに戻る | 指摘内容を反映、品質向上 | 5R 上限超え（Round 6 + Round 7 が必要、5R 化完了条件「最後 2R 連続 clean」未達） |
| 2 | OUT_OF_SCOPE → defer Issue 起票 | 5R 内で defer 完了扱い | 指摘内容（regex 表現）は Construction で確定する事項として「次サイクル」へ繰越は不適切 |
| 3 | TECHNICAL_BLOCKER | - | Markdown table 内 `\|` 表記は実装上回避可能のため不適 |

### 決定

**修正する → 反復レビューに戻る**（選択肢 1）。Round 5 の指摘は regex を Markdown テーブル外のコードブロックに分離する形で修正し、Round 6 + Round 7 の連続 clean で完了条件達成。

### トレードオフと判断根拠

- **得たもの**: 指摘内容の正確な反映、Intent ドキュメントの品質向上、Construction Phase での grep regex の正確な記述参照を保持
- **犠牲にしたもの**: 5R 上限超過（Round 7 まで実施 / レビュー時間増）、5R 化完了条件の解釈について「Round 6 + Round 7 連続 clean」を「最後 2R clean」とみなす運用判断を実施
- **判断根拠**: 修正コストが低い + 指摘自体が妥当 + defer/blocker への該当根拠が弱い、という条件を踏まえ、修正する選択肢が品質と運用を両立する最善

## DR-008: Unit 001 計画レビュー指摘 #1 への対応（Unit 001 スコープ拡大）

- **ステップ**: Construction Phase / Unit 001 計画レビュー（Codex Round 1 / 2026-05-07）
- **日時**: 2026-05-07

### 背景

Codex 計画レビュー Round 1 で「ガードが文書記述の追加に偏っており、実行時に強制できるインターフェースが未定義（手順記述だけだとバイパス可能）」が高優先度の指摘として提出された。Intent line 33 の Unit 001 範囲は「`steps/operations/04-completion.md` §1 / SKILL.md / `feedback_mode=silent` 補足」に限定されており、`skills/aidlc/scripts/lib/retrospective-issue.sh` への実行時ガード追加はスコープ外。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | OUT_OF_SCOPE → defer Issue 起票 | Unit 001 のスコープ厳守、見積もり据え置き | 文書ガードのみではバイパス可能性が残り、jailrun #70 と同型の再発リスクが完全には解消しない |
| 2 | Unit 001 スコープ拡大（実行時ガード取り込み） | 文書 + 実行時の二段防御で再発防止効果が向上、自己適用で本サイクル後続 Unit にも有効化 | 見積もり増（1.5 → 2.5 日相当）、Intent の「含まれるもの」を解釈拡張 |
| 3 | 修正せず受容 | スコープ最小 | 指摘の本質課題を放置 |

### 決定

**選択肢 2: Unit 001 スコープ拡大**を採用。

### トレードオフと判断根拠

- **得たもの**: `retrospective_issue_create` 直前への実行時ガード（対話確認トークンファイル方式）追加により、文書ガードのバイパス経路を構造的に塞ぐ。jailrun #70 と同型の再発リスクを「文書 + 実行時」の二段防御で予防。
- **犠牲にしたもの**: 見積もり 1 日相当の増加、Intent 「含まれるもの」テーブル（line 33）の解釈拡張（明示的な実行時ガード言及は Intent になく、Construction Phase の解釈拡張として扱う）。
- **判断根拠**: ユーザーが明示的に「Unit 001 スコープ拡大」を選択（Codex Round 1 対応の AskUserQuestion 応答）。Intent の主旨「振り返り対話強制ガード強化」を実体的に達成するには文書ガードのみでは不十分との判断。Unit 001 範囲を Intent 文言から解釈拡張する旨を本 DR で明文化することで、Intent 自体の改訂は行わない（マージ前完結契約に整合）。
