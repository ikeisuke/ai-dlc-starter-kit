## DR-001: alpha.3 のスコープ範囲

- **ステップ**: Inception 準備 / Intent 明確化
- **日時**: 2026-06-12

### 背景

v3 リニューアル計画（`docs/v3-renewal-plan.md`）の Phase 3 は「define 実行実装 + develop tiny 実装 + work-item-next.sh + cycle dir 作成ロジック」を束ねている。alpha.3 でこの全体を扱うか、define のみに絞って develop tiny を alpha.4 に分割するかを判断する必要があった。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | Phase 3 全体（+ 前フェーズ defer Issue #731） | 計画どおり進行。define→develop tiny の最小フローが 1 サイクルで「動く」状態になる。defer Issue を溜めない | 1 サイクルのスコープが比較的大きい |
| 2 | define 実行実装のみに絞る | サイクルが小さく安全 | develop tiny が次サイクルに持ち越し、フローが「動く」までに 2 サイクル要する。Phase 進行が計画より細分化 |

### 決定

**選択肢 1（Phase 3 全体 + 前フェーズ defer Issue #731）** を採用。

### トレードオフと判断根拠

- **得たもの**: 計画どおりの Phase 進行。define + develop tiny の最小実行フローを 1 サイクルで確立。alpha.2 レビューで defer した #731 を、define が state を実書き込みする本サイクルで併せて解消
- **犠牲にしたもの**: 1 サイクルあたりのスコープが大きくなる
- **判断根拠**: ユーザーが「Phase3 と前のフェーズで defer した Issue もやろうか」と明示選択。Phase 単位＝サイクル単位の進行（alpha.2 precedent）と整合し、#731 は define の state 実書き込みと密接に関連するため同サイクルで扱うのが合理的

## DR-002: `/aidlc-v3` 起動有効化（marketplace.json 登録）の実施時期

- **ステップ**: Intent 明確化
- **日時**: 2026-06-12

### 背景

alpha.2 skeleton では `marketplace.json` への `aidlc-v3` 登録（`/aidlc-v3` 起動有効化）を「完了条件が手順を読めることであり flow 未実装」を理由に Phase 3+ へ defer していた。alpha.3 で実行実装が入るため、登録を本サイクルで行うか引き続き defer するかを判断する必要があった。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | alpha.3 で登録し起動有効化 | `/aidlc-v3 define` / `develop` を実際に起動・ドッグフーディングでき、設計と実装の乖離を早期検出できる | 一部コマンド（release/reflect/doctor）未実装のまま起動面が露出する |
| 2 | 登録は引き続き defer | 未実装コマンドの起動面を出さない | 実行実装が入っても起動・ドッグフーディングできず、検証はテストハーネス止まり |

### 決定

**選択肢 1（alpha.3 で登録し起動有効化）** を採用。

### トレードオフと判断根拠

- **得たもの**: 実装した define / develop tiny フローを実起動してドッグフーディングできる検証ループ
- **犠牲にしたもの**: release / reflect / doctor が予約のまま起動面に並ぶ（未実装コマンドは案内で停止する想定）
- **判断根拠**: ユーザーが起動有効化を明示選択。実行実装が入る Phase 3 は「試せる」ことの価値が defer 維持のリスクを上回る。v3 state（`.aidlc/state.json`）は v2 と location が異なり共存可能で、v2 への影響もない
