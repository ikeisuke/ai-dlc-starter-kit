## DR-001: 次サイクルのバージョン種別と取り組みテーマ

- **ステップ**: Inception 01-setup（バージョン決定）
- **日時**: 2026-05-06

### 背景

v2.5.1 サイクル完了後、次サイクル開始時に取り組みテーマとバージョン種別を確定する必要があった。前サイクル振り返り Issue は未作成のため、AI 側で v2.5.1 のメタ振り返り由来の Issue 群（#634〜#640）と直近のバグ修正 Issue（#631, #632, #639）を提示してユーザー選択を求めた。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | patch (v2.5.2) | 後方互換維持、スコープ厳守、bugfix 統合に適切 | 大きな機能改修は次回以降に持ち越し |

### 決定

**patch (v2.5.2)** を採用。取り組みテーマは「振り返り関連の調整 + 優先度高いバグ修正」。

### トレードオフと判断根拠

- **得たもの**: 後方互換性厳守による既存ユーザーへの影響最小化、bugfix の即時反映
- **犠牲にしたもの**: 大型振り返り改善（#634, #637）と config 整理（#640）は次サイクル以降へ defer
- **判断根拠**: v2.5.1 の振り返りで顕在化した構造的バグ（#638 / #639）と review-flow の運用実態乖離（#635）は早期解消が必要、かつ後方互換維持で対応可能。`#634` と `#637` は skill / steps の根本改修を含むため scope 別管理が望ましい

## DR-003: review round 上限の改定値（5R）

- **ステップ**: Inception 03-intent / 04-stories-units（成功基準確定）
- **日時**: 2026-05-06

### 背景

v2.5.1 で 6 件の review が上限 3R を超過し、各 review-summary に「上限超過したが指摘軽減傾向のため継続実施」と例外運用記録が残った。新しい round 上限を確定する必要があった。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | 5R に拡張 | 実態（5-6R）に整合、例外運用が消える | 1 review あたりの最大コストが増 |
| 2 | 4R に拡張 | 中庸な拡張 | 4-5R で完了する review がまだ例外扱いになる |
| 3 | 上限撤廃 | 完了条件のみで判定 | 無限ループリスク、進捗判断が困難 |

### 決定

**選択肢 1（5R）** を採用。あわせて完了条件を「最後 2 round 連続で指摘ゼロまたは defer 化」に改定。

### トレードオフと判断根拠

- **得たもの**: v2.5.1 の例外運用 6 件すべてが正常運用となる、収束判定の安定性
- **犠牲にしたもの**: 1 review あたりの上限コストが 67% 増（3→5）
- **判断根拠**: 実証データ上 5R で大半が収束、「最後 2 round 連続ゼロ」完了条件で 5R 未満でも収束可能性を確保。実際本 Inception の User Stories レビューは 9 round、Unit 定義レビューは 7 round で完了しており、5R+完了条件の妥当性を自己実証

## DR-004: defer 判定の自動 Issue 起票（必須ラベル仕様の確定）

- **ステップ**: Inception 04-stories-units（ストーリー 1B 受け入れ基準確定）
- **日時**: 2026-05-06

### 背景

v2.5.1 で「ユーザー判断に委ねる」「Issue 化保留」とした defer 指摘が後で漏れ、Operations Phase で再出して千日手化した。defer 判定時に AI agent が即時起票する仕組みが必要だが、ラベル仕様が未確定だった。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | 必須: backlog + type:defer-from-review、任意: Unit/priority ラベル | 識別キーが明確、検索容易 | ラベル未存在時に起票成功と判定する余地 |
| 2 | 必須: backlog のみ | 最小限 | defer 由来か通常 backlog かの区別がつかない |
| 3 | 必須なし（自由フォーマット） | 制約最小 | 検索・自動化が困難 |

### 決定

**選択肢 1** を採用。ラベル未存在時の挙動を補強するため、起票後に `gh issue view --json labels` で必須ラベル両方の付与を検証し、欠落時は `PENDING_MANUAL` 扱いに統一する仕様を追加。

### トレードオフと判断根拠

- **得たもの**: defer 由来 Issue の検索可能性、識別キーの明確化、ラベル未存在時の運用ギャップ解消
- **犠牲にしたもの**: 起票後 1 回追加で `gh issue view` を呼ぶコスト
- **判断根拠**: defer 漏れの構造的防止が本サイクルの主要目的の一つであり、運用ギャップを残さないことが優先

## DR-005: Round 4 以降の新領域判定の正準（領域キー差分）

- **ステップ**: Inception 04-stories-units（ストーリー 1C 受け入れ基準確定）
- **日時**: 2026-05-06

### 背景

v2.5.1 の Operations round 4 で AIDLC_PROJECT_ROOT 領域（Unit 002/004 横断）の新規指摘が発生し、千日手抜け出しのため defer して Issue #631/#632 化した。同型問題の構造的防止には新領域判定の機械的再現可能ルールが必要。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | 領域キー差分による準機械判定（一次）+ パス記録（二次補助根拠） | 機械的再現可能、判定揺らぎ最小 | 領域キー定義が必要 |
| 2 | パス完全一致による比較 | 単純 | ファイル単位の差分が大量に出るため新領域判定が機能しない |
| 3 | AI agent の自由判断 | 柔軟 | レビュアー間で揺らぎ、Testable を満たさない |

### 決定

**選択肢 1** を採用。境界条件として領域キーを完全列挙＋第一階層フォールバック規則を定義。判定手順 0〜7 を機械的に固定（パス抽出→正規化→ソート→差分→JSON 記録→true/false 判定）。

### トレードオフと判断根拠

- **得たもの**: 新領域判定の Testable 化、レビュアー間の判定揺らぎ解消
- **犠牲にしたもの**: 境界条件テーブルの保守コスト（新ディレクトリ追加時の更新）
- **判断根拠**: 千日手抜け出しの実証データに基づく構造的解決を優先

## DR-006: 既存違反の allowlist 機構（出口条件付き）

- **ステップ**: Inception 04-stories-units（Unit 002 責務確定）
- **日時**: 2026-05-06

### 背景

`bin/check-test-isolation.sh` 導入時に既存 BATS テストの違反が大量に検出される可能性があり、Unit 002 のクリティカルパスが不安定になるリスクがあった。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | 出口条件付き allowlist（追加日/理由/期限/追跡Issue 必須）+ CI で期限切れ・stale を fail | 既存違反隔離 + 陳腐化防止 | allowlist 形式の保守コスト |
| 2 | 既存違反を本 Unit 内で全修正 | 即時クリーン | Unit 002 のスコープ過大、見積もり不安定 |
| 3 | 単純 allowlist（メタ情報なし） | 実装単純 | 陳腐化リスク、新規違反混入時の判定困難 |

### 決定

**選択肢 1** を採用。TSV 形式（`file_path<TAB>function_name<TAB>reason<TAB>added_date<TAB>tracking_issue<TAB>expiry_date`）で必須メタ情報を持たせ、照合キーは `file_path + function_name + reason` の 3 つ組とする。

### トレードオフと判断根拠

- **得たもの**: Unit 002 のクリティカルパス短縮、既存違反の段階解消を後続サイクルへ計画的に分離可能
- **犠牲にしたもの**: allowlist 仕様の実装と維持コスト
- **判断根拠**: 既存違反の一括修正は scope 不確定で見積もりが破綻するため、隔離→計画解消の二段階方式が現実的

## DR-008: Operations 7.12 Squash の実装方式（git reset --soft）

- **ステップ**: Inception 04-stories-units（Unit 004 実装方式確定）
- **日時**: 2026-05-06

### 背景

Operations 7.12 PR レビュー反映コミットを squash する実装方式として、`git rebase --interactive` と `git reset --soft + git commit` の選択が必要だった。AI-DLC は非対話実行が前提のため対話エディタ依存を避ける必要がある。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | git reset --soft + git commit | 完全非対話、シンプル、rollback は git reset --hard ORIG_HEAD | 履歴粒度の細かい制御は不可（全コミット 1 つに統合） |
| 2 | git rebase --interactive + GIT_SEQUENCE_EDITOR=: | 細かい制御可能 | 環境変数依存、コンフリクト時の rollback 複雑 |
| 3 | git rebase --interactive（標準） | 確立された方式 | 対話エディタ依存、AI-DLC で動作不安定 |

### 決定

**選択肢 1** を採用。NFR セキュリティの rollback 契約を `git reset --hard ORIG_HEAD` に統一。

### トレードオフと判断根拠

- **得たもど**: 完全非対話実装による AI-DLC 自動実行との整合、rollback シンプル化
- **犠牲にしたもの**: コミット履歴の細かい制御は不可（本 Unit のスコープでは不要）
- **判断根拠**: Operations 7.12 で発生する複数 round のレビュー反映コミットは 1 コミットに統合するのが目的であり、細かい制御は不要。非対話前提を最優先

## DR-009: release_prep_commit slot の記録媒体（progress.md 一本化）

- **ステップ**: Inception 04-stories-units（Unit 004 受け入れ基準確定）
- **日時**: 2026-05-06

### 背景

Squash 起点となる 7.7 完了時の commit hash をどこに記録するかが論点だった。progress.md / 環境変数 / 別ファイルの 3 案が候補。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | progress.md の HTML コメント形式で記録 | 既存固定スロット（spec §7.4）と整合、永続化、grep で抽出可 | progress.md フォーマット規約への新規 slot 追加 |

- **判断根拠**: 環境変数案はセッション間永続性なし、別ファイル案は progress.md スロット管理と二重化、progress.md 一本化が最も整合的

## DR-010: 4 Unit 構成と依存関係の分類（hard / soft）

- **ステップ**: Inception 04-stories-units（Unit 依存関係確定）
- **日時**: 2026-05-06

### 背景

4 Unit（A: review-flow / B: CI チェック / C: AIDLC_PROJECT_ROOT / D: Operations squash）の依存関係をどう分類するかが論点。Unit A 依存を hard とすると並列実装可能性が落ち、soft とすると review 運用前提が曖昧になる。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | A → B/C/D は soft（レビュー運用前提）、B → C/D は hard（CI hook 実装依存） | 実装着手と review 実施を分離、並列性確保 | 依存記述の複雑化 |
| 2 | A → B/C/D も hard | 単純 | 実装並列性を不要に落とす |
| 3 | 全 Unit を独立にする | 最大並列性 | 自己適用の閉ループが機能しない |

### 決定

**選択肢 1** を採用。各 Unit 定義の「依存する Unit」セクションで hard / soft を明示する。

### トレードオフと判断根拠

- **得たもの**: 実装並列性の確保（A の実装中でも B/C/D の実装着手可能）、review 運用前提の明確化
- **犠牲にしたもの**: 依存記述の複雑化
- **判断根拠**: AI-DLC の Construction Phase は通常逐次実行だが、依存性の正確な記述は将来の並列実装機能（#441）への準備にもなる

## DR-012: PRFAQ の作成（patch でも standard depth では作成）

- **ステップ**: Inception 04-stories-units（PRFAQ ステップ）
- **日時**: 2026-05-06

### 背景

depth_level=standard では PRFAQ は実行必須だが、本サイクルは patch リリースのメタ開発内部のため対外コミュニケーションの実用価値が低い。スキップ vs 作成の判断が必要だった。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | PRFAQ を作成（standard depth 規約に従う） | スキル規約遵守、サイクル全体像の整理になる | 内部リリースのため外部公開価値は限定的 |
| 2 | スキップとして記録 | 工数削減 | depth_level=standard の規約違反リスク |

### 決定

**選択肢 1** を採用。standard depth の規約を遵守。内容は本サイクルの 4 Unit を整理した内部向け PRFAQ として作成。

### トレードオフと判断根拠

- **得たもの**: スキル規約遵守、サイクル全体像のドキュメント化（FAQ 形式での想定質問への先回り回答）
- **犠牲にしたもの**: PRFAQ 作成工数（短時間で完了）
- **判断根拠**: standard depth の規約は意図的にスキップ可能性を minimal のみに限定しており、これに従うのが安全
