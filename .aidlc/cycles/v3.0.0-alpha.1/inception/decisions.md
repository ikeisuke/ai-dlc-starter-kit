# 意思決定記録 - v3.0.0-alpha.1

## DR-001: 今サイクルのスコープを Phase 1（RFC / data model 固定）に限定

- **ステップ**: Inception 開始（スコープ確定）
- **日時**: 2026-06-10

### 背景

`docs/v3-renewal-plan.md` は v3 フルリニューアルを 7〜8 サイクルに分割する計画。「v3.0.0 の構築を進めたい」という入力に対し、1 AI-DLC サイクルでどこまでをカバーするか決める必要があった。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | Phase 1 のみ（RFC 固定） | 設計を先に固め後続のブレを防ぐ。計画書推奨の「最初の一手」 | 「動くもの」はまだ得られない |
| 2 | Phase 1〜3（動くまで） | 初めて動く v3 が手に入る | Unit 数が多く大規模サイクル化 |
| 3 | v3.0.0 全体を 1 サイクル | 一括完了 | 巨大化・承認ゲート形骸化（計画書が分割を明示） |

### 決定

**Phase 1 のみ（RFC 固定）** を採用。段階的進行（1 alpha = 1 フェーズ）。

### トレードオフと判断根拠

- **得たもの**: 設計判断の早期確定。後続フェーズの手戻り防止。レビュー可能な小さい単位
- **犠牲にしたもの**: 本サイクルでは実行可能な v3 が得られない（docs-only）
- **判断根拠**: 計画書自身が「ここでの設計判断が Phase 2 以降の全実装の土台」と明記。段階的に確実に進める方針とユーザーの「段階的に進める」意向に合致

## DR-002: バージョンを v3.0.0-alpha.1 とし alpha 段階リリースを採用

- **ステップ**: Inception 開始（バージョン決定）
- **日時**: 2026-06-10

### 背景

現在最新は v2.6.6。v3 開発の各サイクルにどのバージョン名を与えるか（v3.0.0 を最初から名乗るか、dev 増分にするか）を決める必要があった。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | v3.0.0 | 計画書 data-model 例と一致 | v3.0.0 を最終リリースにしたい場合に番号設計が崩れる |
| 2 | v2.7.0 | dev 増分とリリース番号を分離 | v3 作業が v2 系番号で見えにくい |
| 3 | v3.0.0-alpha.1 | v3 プレリリースと明示。alpha.1/2/3... で段階進行 | プレリリース接尾辞の運用が必要 |

### 決定

**v3.0.0-alpha.1** を採用。alpha.1 → alpha.2 → alpha.3 ... と進め、全 alpha 完走後に v3.0.0 を main へ。

### トレードオフと判断根拠

- **得たもの**: dev であることが番号から明白。v3.0.0 を最終リリースに温存
- **犠牲にしたもの**: プレリリース接尾辞のディレクトリ・タグ運用
- **判断根拠**: 段階的開発の各増分を明示でき、最終 v3.0.0 リリースと整合する

## DR-003: ブランチトポロジを 2 段構え（v3.0.0 ベース ← cycle/alpha）に

- **ステップ**: Inception セットアップ（ブランチ確認）
- **日時**: 2026-06-10

### 背景

AI-DLC 標準は cycle ブランチ → main への PR。今回は alpha を段階的に統合してから main へ入れたいため、トポロジの起点と作業ブランチ方式を決める必要があった。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | v3.0.0 を v3/renewal-plan 起点 + cycle/alpha を切る | plan doc が v3 系列に含まれる。alpha ごとに独立レビュー/ロールバック | 2 段構えで標準フローと差異 |
| 2 | v3.0.0 を main 起点 | クリーンな出発 | plan doc が含まれず別途持ち込みが必要 |
| 3 | v3.0.0 上で直接作業 | PR 工程が減る | alpha ごとの独立レビューが困難 |

### 決定

**v3.0.0 を v3/renewal-plan 起点に作成し、cycle/v3.0.0-alpha.1 を切る**。release で cycle → v3.0.0 の PR、全 alpha 後に v3.0.0 → main。

### トレードオフと判断根拠

- **得たもの**: plan doc が v3 系列に含まれる。alpha 単位のクリーンなレビュー・マージ・ロールバック
- **犠牲にしたもの**: AI-DLC 標準（cycle → main）からの逸脱。Operations の PR base を v3.0.0 に向ける運用調整が必要
- **判断根拠**: 段階統合戦略に最も適合し、計画書の入力（plan doc）を v3 系列に自然に取り込める

## DR-004: 計画書の設計判断 6 件を RFC で「一から」検討する

- **ステップ**: Intent 作成
- **日時**: 2026-06-10

### 背景

計画書「判断が必要なポイント」6 件（コマンド名 / Express / v2 EOL / review 統合 / GitHub 前提 / state format）には推奨案がある。これを RFC でどう扱うか（固定 / 一部再検討 / 全てオープン）を決める必要があった。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | 計画書推奨を全て固定 | 手戻り少・速い | 検討不足のまま確定するリスク |
| 2 | 一部をオープン | バランス | どれをオープンにするか追加判断が必要 |
| 3 | 全てオープン（RFC で一から） | 各案の trade-off を改めて評価し納得感のある結論 | 工数増 |

### 決定

**全てオープン（RFC で一から検討）** を採用。計画書推奨は一入力に留め、結論が分かれうる論点は承認ゲートでユーザー確認する。

### トレードオフと判断根拠

- **得たもの**: v3 の根幹設計を改めて吟味した上で確定できる。後続全フェーズの土台の納得感
- **犠牲にしたもの**: RFC 執筆工数（Unit 001 が最大の Unit に）
- **判断根拠**: 6 件は v3 全体を方向づける根幹であり、Phase 1 の主目的そのもの。ここで一から検討する価値が工数を上回る

## DR-005: Phase 1 を 4 Unit（文書単位）に分割

- **ステップ**: Unit 定義
- **日時**: 2026-06-10

### 背景

Phase 1 の成果物は 4 つの設計文書 + schema + template。計画書では Phase 1 全体を「Unit 001」と呼ぶが、AI-DLC サイクル内での Unit 粒度を決める必要があった。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | 4 Unit（rfc/workflow/data-model/migration） | 各文書が独立価値単位。段階的レビューが容易 | Unit 数が増える |
| 2 | 1 Unit（計画書の Unit 001 のまま） | 計画書と一致 | 巨大な単一 build・単一レビューで非段階的 |

### 決定

**4 Unit（文書単位）** を採用。依存は RFC(001) 起点の DAG（002/003→001、004→001+003）。

### トレードオフと判断根拠

- **得たもの**: 文書ごとの独立レビュー・段階的 build。依存関係の明示
- **犠牲にしたもの**: Unit 管理オーバーヘッドの微増
- **判断根拠**: 4 文書は依存はあるが独立して価値を持つ。段階進行方針（DR-001）と整合
