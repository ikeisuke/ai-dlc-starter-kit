# 意思決定記録 - v3.0.0-alpha.4

## DR-001: サイクルバージョンの決定（alpha.4 を採用）

- **ステップ**: セットアップ（バージョン決定）
- **日時**: 2026-06-18

### 背景

v3.0.0 系 alpha.1/2/3 の後継として、振り返り #733 の構造改善（T1/T2'/T4/T6）を行うサイクルのバージョンを確定する必要があった。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | v3.0.0（GA） | alpha 群を束ねた正式リリース。suggest-version の major 提案と一致 | 構造改善の検証前に GA を切ることになる |
| 2 | v3.0.0-alpha.4 | 構造改善を alpha でもう一段検証してから GA に進める | リリースが1サイクル分後ろ倒し |

### 決定

**v3.0.0-alpha.4** を採用

### トレードオフと判断根拠

- **得たもの**: GA 前に parser 構造改善を検証する安全マージン
- **犠牲にしたもの**: GA タイミングの後ろ倒し
- **判断根拠**: #733 の主因（パース安全境界の反復再発）を断つ構造改善は GA 品質に直結するため、GA 前に alpha で検証する方が安全と判断（ユーザー選択）

## DR-002: ブランチ方針（cycle/v3.0.0 を新規作成）

- **ステップ**: セットアップ（ブランチ確認）
- **日時**: 2026-06-18

### 背景

開始時のブランチが `v3.0.0`（`cycle/*` 命名でない）であり、メタ開発のブランチ命名規約（`cycle/vX.X.X`）との整合をどう取るか判断が必要だった。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | 現在の v3.0.0 で続行 | ブランチ名がサイクルと一致・git clean | `cycle/*` 命名規約から外れる |
| 2 | cycle/v3.0.0 を新規作成 | 命名規約に整合。v3.0.0 統合ラインとして alpha 増分を集約 | サイクル名（alpha.4）とブランチ名（v3.0.0）が非対称 |

### 決定

**cycle/v3.0.0 を新規作成**（現 v3.0.0 HEAD = alpha.3 マージ済みから分岐）を採用

### トレードオフと判断根拠

- **得たもの**: メタ開発のブランチ命名規約への整合、v3.0.0 ラインの統合ブランチ
- **犠牲にしたもの**: サイクル名（alpha.4）とブランチ名（v3.0.0）の対称性
- **判断根拠**: ブランチ `cycle/v3.0.0` を v3.0.0 統合ラインとし、alpha 増分（alpha.4 等）を cycle ディレクトリで区別する構成が規約と整合（ユーザー選択）

## DR-003: 本サイクルに含める Try セットの選択（T1+T2'+T4+T6）

- **ステップ**: Intent明確化
- **日時**: 2026-06-18

### 背景

#733 は構造対策として T1（共有 parser 集約）を主対策とし、T2'（conformance test）/ T4（機械検出）/ T6（CycleResolver）を付随対策として提示。本 alpha サイクルにどこまで含めるか確定が必要だった。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | T1 のみ | スコープ最小・確実 | 再発防止のガードレール（test/CI）が欠け、ローカル実装の再混入余地が残る |
| 2 | T1+T2'+T4+T6 | 主対策 + 実行可能契約 + 機械検出 + P4 回帰固定まで締める | スコープ拡大、1 alpha の作業量増 |

### 決定

**T1 + T2' + T4 + T6** を採用

### トレードオフと判断根拠

- **得たもの**: 「共有する」だけでなく禁止規約・conformance・CI 検出まで含めた構造的再発防止
- **犠牲にしたもの**: 1 alpha サイクルの作業量増
- **判断根拠**: #733 のセルフ+Codex 独立レビュー結論「T1 単独は再発防止チェック逃げ。ガードレール（実行可能契約/機械検出）まで含めて締める」に従う（ユーザー選択）

## DR-004: T4 禁止パターン機械検出の実装先（CI チェック）

- **ステップ**: Intent明確化
- **日時**: 2026-06-18

### 背景

T4 の機械検出を doctor コマンドに載せるか CI に載せるかで実装規模・即効性が変わる。v3 の doctor コマンドは未実装（予約）。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | CI チェック | 既存 CI 基盤に乗り即効。doctor 未実装に依存しない | doctor 経由のローカル診断は別途必要 |
| 2 | doctor コマンド新設 | ローカル診断に統合 | doctor の設計・実装コストで alpha が重くなる |
| 3 | 両方 | 最も堅牢 | スコープ最大 |

### 決定

**CI チェック** を採用

### トレードオフと判断根拠

- **得たもの**: 最短経路での自動ガード。doctor 未実装への非依存
- **犠牲にしたもの**: ローカル診断（doctor）統合は別サイクルに先送り
- **判断根拠**: doctor が未実装・予約状態であり、CI が既存基盤に乗って即座に機能するため（ユーザー選択）

## DR-005: T6 CycleResolver の扱い（v3 に回帰テストのみ追加）

- **ステップ**: Intent明確化
- **日時**: 2026-06-18

### 背景

brownfield 解析により、v3 本体には gitlog 推定ロジックが存在せず cycle は `state.json.current_cycle`（明示指定）に一本化済みと判明。#733 P4 で誤った cycle（v2.6.6）を返した CycleResolver は framework 側（`skills/aidlc/`）の可能性が高い。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | v3 に回帰テストのみ追加 | v3 の明示指定一本化を仕様として固定。スコープ最小 | framework 側の実体修正は別途必要 |
| 2 | framework 側の対象を特定して修正 | P4 の実体を直接解消 | v3 GA スコープ外に広がる |
| 3 | defer（別サイクル） | alpha を parser 集約に集中 | T6 の固定が後回し |

### 決定

**v3 に回帰テストのみ追加** を採用

### トレードオフと判断根拠

- **得たもの**: v3 本体の明示指定優先仕様を回帰テストで固定し再発防止
- **犠牲にしたもの**: framework 側 CycleResolver の実体修正は本サイクル対象外
- **判断根拠**: v3 本体は既に明示指定一本化済みで、回帰テストで仕様を固定すれば v3 での P4 再発は防げる。framework 側は v3 GA スコープ外（ユーザー選択）

## DR-006: Unit 分解方針（T1+T2' を Unit 001 に統合）

- **ステップ**: Unit定義
- **日時**: 2026-06-19

### 背景

Try は T1/T2'/T4/T6 の4項目。Unit を Try と1:1（4 Unit）にするか、密結合する T1（リファクタ）と T2'（その検証契約）を統合するかの設計判断が必要だった。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | Try と 1:1（4 Unit） | #733 の Try との traceability 最大 | T1 単独 Unit が「behavior-preservation を検証する手段（T2'）」を持たず、リファクタ Unit として独立検証不能（INVEST-Testable 不足） |
| 2 | T1+T2' を Unit 001 に統合（3 Unit） | リファクタとその conformance 検証が1ブロックで独立検証可能 | Try と Unit が 1:1 でなくなる |

### 決定

**T1+T2' を Unit 001 に統合（Unit 001=T1+T2' / 002=T4 / 003=T6 の3 Unit）** を採用

### トレードオフと判断根拠

- **得たもの**: リファクタ Unit が自身の behavior-preservation を conformance test で保証する独立検証可能性（INVEST-Testable）
- **犠牲にしたもの**: Try と Unit の 1:1 traceability（各 Unit 内に Try 対応を明記して緩和）
- **判断根拠**: 共有 parser への集約は純粋リファクタであり、境界を壊さないことの検証（T2'）と不可分。検証手段を持たない T1 単独 Unit は安全に完了判定できないため統合が適切と判断（AI 設計判断 / 各 Unit に Try 対応を明記してトレーサビリティを確保）
