# PRFAQ: AI-DLC スターターキット v2.6.5

## Press Release（プレスリリース）

**見出し**: AI-DLC スターターキット v2.6.5、サイクル運用の摩擦を 5 箇所同時に解消

**副見出し**: Unit 重複検出 / 設計レビュー反復予防 / マージ前完結契約最終確認 / defaults.toml 同期ガード / 委譲フロー自動継続。5 つの構造的改善で「同じミスが繰り返される」体験を構造的に削減します。

**発表日**: 2026-05-17 想定

**本文**:

[背景] v2.6.3 / v2.6.4 サイクルの運用を通じ、(1) Inception で他サイクル完了 Unit と重複した Unit 起案 (v2.6.4 Unit 001 取り下げ事例)、(2) Construction Phase 1 で既存実装を Read せず設計起草 → Round 1 設計レビュー反復、(3) Operations §7.13 マージ後に cycle 成果物を改変 → branch protection reject → rollback、(4) defaults.toml の二重 SoT 同期漏れによる CI 修復コミット (修復コミット 421c5ac1)、(5) `/aidlc r` 等の委譲フローで案内テキスト経由の UX 摩擦、という同一構造の課題が複数回観測された。これらは「個別 PR で都度修正」しても再発する性質のものであり、starter kit 本体のフロー・テンプレ・CI ガード・委譲規約に構造的に組み込むことで初めて予防可能となる。

[プロダクト] v2.6.5 は対応する 5 OPEN Issue (#712 / #679 / #641 / #714 / #717) を 1 サイクルに集約し、それぞれ Inception ステップ / Construction Plan テンプレ + reviewing-construction-design 観点 / Operations §7.13 直前 AskUserQuestion / `.github/workflows/` の CI ジョブ / `skills/aidlc/SKILL.md` 独立フロー委譲セクションに改修を入れる。各改修はサイクル自身でドッグフーディング検証され、改修と検証が同一サイクル内で完結する。

[顧客の声] スターターキット利用者（Visitory プロジェクト等の consumer プロジェクト開発者およびスターターキット自身のメタ開発担当）から: 「Unit 起案前に重複チェックがあれば v2.6.4 の取り下げ作業は要らなかった」「`/aidlc r` の案内テキストを介さず直接振り返りが始まるのは UX として明確な改善」「マージ前完結契約の最終確認があれば post-merge cleanup での記録漏れに毎回気付ける」。

[今後の展開] U4 の追加達成条件として Unit 完了処理段階での自動同期スクリプト同梱を v2.6.x 系で検討。U2 の派生改修 (#633 / #692) は別サイクルで集約予定。defaults.toml の構造変更 (共通テンプレ展開) は別 epic で別途検討。

## FAQ（よくある質問）

### Q1: なぜ 5 件を 1 サイクルに集約したのか？

A: 5 件はそれぞれ「同一構造の運用課題への構造的予防」というカテゴリで重なる一方、対象スキル / 対象パスが分離しているため依存関係がほぼ無く、並列実装に適しているため。サイクル粒度を細分化すると Inception / Construction / Operations フェーズが毎サイクル繰り返されオーバーヘッドが大きくなる。

### Q2: patch (v2.6.5) として妥当か？ minor / major に該当する破壊的変更は含まれないか？

A: 5 件すべて既存フローへの追加・観点強化・ガード追加であり、既存挙動を破壊しない。デフォルト値変更や API 互換性破壊は含まれない。CI ガード追加 (#714) のみ「これまで pass していた状態が fail になる」可能性があるが、これは既存サイクル成果物の品質チェック強化であり機能の後方互換性破壊ではない。

### Q3: consumer プロジェクトへの影響は？

A: #712 / #679 / #641 / #717 は consumer プロジェクトの AI-DLC フローを直接強化する（自動的に新フローで動作）。#714 の CI ガードは starter kit 自己リポジトリ専用ジョブとして配置し、consumer プロジェクトへは配布しない（CLAUDE.md「ドッグフーディング特殊処理を本体に埋めない」原則準拠）。

### Q4: 各改修の検証はどう担保するか？

A: 各 Unit がドッグフーディング検証を受け入れ基準に含む。具体的には U1 = 本サイクル自身の Inception で重複チェック実証 (本 PRFAQ 起草時点で実施済み、結果: 予定 U1〜U5 スラグは v2.6.3 / v2.6.4 完了 Unit と一致なし)、U2 = U2 自身の plan に事前コード Read セクションが書かれる、U3 = 通常経路 (a) を Operations Phase で実機検証、U4 = 同期崩し→CI red→復元→green の遷移検証、U5 = Claude Code 実機で `/aidlc r` 直接開始確認。

### Q5: Codex CLI / Gemini CLI の挙動検証は？

A: Codex CLI 実機での U5 検証は追加達成条件 (任意) として Operations Phase 振り返り前段で実施。Gemini CLI は環境未整備のため検証範囲外 (記録のみ)。U5 必須側は Claude Code 実機検証で成立する。
