# 意思決定記録（v2.6.1 Inception Phase）

Inception Phase で行われた主要な意思決定を記録する。

## DR-001: v2.6.1 patch リリース化（v2.7.0 minor リリースを採らない）

- **決定日**: 2026-05-10
- **決定内容**: 本サイクルを **v2.6.1 patch リリース** として位置づけ、v2.6.0 リリース後に検出された 5 件のバグ・UX 退行・規約一貫性不足・CI ノイズの解消に専念する。v2.7.0 minor リリースを今サイクルで実施しない
- **背景**: v2.6.0 リリース直後に Issue #688（致命的 OOM クラッシュ）/ #690（UX 退行）等が短期間で集中検出された。v2.7.0 で取り組むべき振り返り由来項目（#691/#692/#693/#694）と切り分け、安定性確保を優先する判断が必要だった
- **選択肢**:
  | 案 | 概要 | メリット | デメリット |
  |----|------|---------|----------|
  | A | v2.6.1 patch（採用） | 小スコープで短期完了、安定化に専念。v2.6 系を確実に運用フェーズへ移せる | minor 機能追加が後ろ倒し |
  | B | v2.7.0 minor（patch 統合 + 振り返り由来も全件取込） | 1 サイクルで広範な改善 | スコープ肥大、レビュー重複・回帰リスク増加、リリース時期遅延 |
  | C | patch + 振り返り由来 1〜2 件選択取込（折衷） | バランス | 選定基準の判断コスト、Issue 単位の関連性吸収にズレ |
- **トレードオフ**: 機能追加・改善の幅を狭め（犠牲）、その代わりに安定性確保とレビュー往復削減・短期リリースを得る（獲得）
- **判断根拠**: ユーザー指示「2.6.1 として 2.6.0 での対応に関連したバグや機能の調整をすすめたい」に直接合致。v2.6.0 で実装された GitHub Projects 移行基盤・squash-unit.sh CI チェック opt-in 化など新機能の安定運用を優先することで、v2.7.0 における振り返り由来 reviewing 改善（評価軸追加）に集中できる土台を整える
- **影響範囲**: Intent / ユーザーストーリー / Unit 数 / Operations Phase の release 範囲
- **再検討条件**: 本サイクル内で重大な追加バグが発見され patch スコープを越える対応が必要になった場合、または 5 Unit のいずれかが想定外に肥大した場合は本決定を再評価する

## DR-002: Issue #691（squash-unit.sh の汎用 CI チェックをスキル本体に取り込む設計検討）を v2.7.0 へ送る

- **決定日**: 2026-05-10
- **決定内容**: 振り返り由来の Issue #691（priority: high）を本サイクル v2.6.1 のスコープに含めず、v2.7.0 サイクルで取り組む
- **背景**: #691 は Issue #687（squash-unit.sh の CI 構造チェック設定駆動化）と同じファイル `squash-unit.sh` が対象だが、スコープが「設計検討（スキル本体への汎用化取り込み）」と大きい。1 サイクル内で #687 の設定駆動化と #691 の構造変更を同時に行うと patch サイクルの責務が肥大化する
- **選択肢**:
  | 案 | 概要 | メリット | デメリット |
  |----|------|---------|----------|
  | A | スコープ外 / 次サイクル（採用） | patch サイクル責務維持、v2.7.0 で #687 を踏まえた整合的な設計検討が可能 | priority high 項目の解消が 1 サイクル遅れる |
  | B | #687 と統合実装 | 同ファイルの二重修正回避 | patch サイクルが肥大、設計検討と実装が混在し分割レビュー困難 |
  | C | #687 を取り下げ #691 単独で実装 | 1 件単位 | #687（priority: medium）を v2.6.1 で解消できず、即時のメンテナビリティ改善が遅れる |
- **トレードオフ**: 振り返り由来項目の即時解消（犠牲）、その代わりに patch サイクルの整合性と #687→#691 の段階的な進化経路（獲得）
- **判断根拠**: ユーザー指示と整合（「振り返り結果も小さければ取り込みたい」が、#691 は設計検討課題で粒度が大きい）。#687 の設定駆動化が完了した後に #691 の汎用化検討を行うほうが、設計選択肢が広がり再構成コストが下がる
- **影響範囲**: 振り返り由来 Issue 4 件（#691/#692/#693/#694）の v2.7.0 への送り出し方針全体
- **再検討条件**: v2.7.0 サイクル開始時、#687 の実装結果を踏まえて #691 の設計方針を再評価する

## DR-003: Unit 数を 5 件固定とする（Issue 1 件 = 1 Unit のマッピング）

- **決定日**: 2026-05-10
- **決定内容**: 本サイクルは **5 Unit 固定** とし、Issue（#688/#686/#690/#689/#687）と Unit を 1:1 対応させる。例外的な追加・分割が必要な場合は Construction Phase で再計画し Intent 改訂を伴う
- **背景**: 5 Issue はすべて互いに独立（依存関係は Unit 003/005 → Unit 004 の推奨依存のみ、強制依存なし）。粒度がほぼ揃っており、Issue を Unit 内で統合・分割するメリットが小さい。AI レビュー（reviewing-inception-stories Round 1 指摘 #5）でも S5 の AC 肥大が指摘されたが、`run_internal_ci_checks_or_skip()` 単一関数に閉じる構造であり PR としては 1 Unit 完結が妥当
- **選択肢**:
  | 案 | 概要 | メリット | デメリット |
  |----|------|---------|----------|
  | A | 5 Unit 固定（採用） | Issue トレーサビリティ最大、Construction の並行実行容易、Unit 単位での独立 review/merge | S5 が他 Unit より AC 数が多くなる |
  | B | S5 を「設定キー導入」「fallback」「テスト拡張」に 3 分割（合計 7 Unit） | 各 Unit の AC 数を均等化 | Issue ↔ Unit のマッピングが複雑化、Construction の並行実行 / squash 単位がぶれる |
  | C | 5 Issue を 3〜4 Unit に統合（例: #687+#691、#689+#690） | Unit 数最小化 | スコープ肥大、Issue close タイミングと Unit 完了タイミングが乖離、レビューサマリ複雑化 |
- **トレードオフ**: S5 の AC 数均等化（犠牲）、その代わりに Issue トレーサビリティ・並行実行・1 Unit = 1 PR 単位の単純さ（獲得）
- **判断根拠**: AI レビュー指摘 #5（S5 肥大）に対しては Story 内で「段階的構造化（5 ブロックの AC、Construction での順次実装）」を Small/Estimable 補足として明記することで吸収。Unit を分割するより Construction Phase 内のタスク管理機能で段階管理するほうが、5 件すべての Issue が並行進行する patch サイクルのリズムに合う
- **影響範囲**: Construction Phase の Unit 進行管理、Operations Phase の squash・release 範囲
- **再検討条件**: Construction Phase 着手時に S5 の実装が単一関数 `run_internal_ci_checks_or_skip()` に閉じない構造変更を伴うと判明した場合、Unit 005 を分割し Intent を改訂する

## DR-004: 各 Issue の修正方針確定は Construction 設計レビューに委ねる

- **決定日**: 2026-05-10
- **決定内容**: Inception Phase 時点で複数案ある修正方針（#688 の CLI モード追加 / 専用ラッパー / SKILL.md 改訂、#687 の設定キー名・配置先など）は確定せず、Construction Phase の設計レビューで AI / 人間レビューを通して採用案を確定する
- **背景**: Intent / Story では「振る舞い・受け入れ基準」を中心に定義し、実装手段の固定は最小限にとどめる方針（reviewing-inception-stories Round 1 指摘 #6 で「AC が実装手段に寄りすぎ」を反映済）。複数の有効案がある場合、設計レビューでメリット・デメリットを比較する余地を残す
- **選択肢**:
  | 案 | 概要 | メリット | デメリット |
  |----|------|---------|----------|
  | A | Construction で確定（採用） | 設計レビューで複数案比較、変化に強い | Inception 時点では「実装案複数」の状態で進める |
  | B | Inception で確定 | 計画段階で全方針が固まる | 設計レビューの責務希薄化、変更時に Intent 改訂が必要 |
- **トレードオフ**: Inception 時点での確定感（犠牲）、設計レビューの実効性と変更耐性（獲得）
- **判断根拠**: AI-DLC の標準フロー（Construction Phase 1 で設計、Phase 2 で実装）に従う。Intent では振る舞い・受け入れ基準を SoT とし、実装手段は設計レビューで決定するのが本来の責務分担
- **影響範囲**: Construction Phase の Phase 1（設計）の範囲・期間
- **再検討条件**: 設計レビューで採用案が決まらず複数 round に渡る場合、本サイクルでは defer して v2.7.0 へ持ち越す可能性を再検討する
