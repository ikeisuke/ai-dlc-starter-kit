# PRFAQ: AI-DLC Starter Kit v2.6.3

## Press Release（プレスリリース）

**見出し**: AI-DLC Starter Kit v2.6.3 — 規約 SoT・AI 実行再現性・セキュリティ・保守性を底上げする patch リリース

**副見出し**: v2.6.2 の振り返り・Codex レビュー指摘・実運用フィードバック由来の 7 件のバックログ Issue を解決し、AI エージェント駆動開発の足回りをより堅牢にする

**発表日**: 2026-05（v2.6.3 サイクル完了時）

**本文**:

[背景] v2.6.2 サイクルでは、CI を停止させた bash dynamic scope shadowing バグ、`codex exec` の stdin ハング、パストラバーサル検証の抜け、属人化したマージ前 CI 修復フロー、`/aidlc v` のバージョン誤推測など、AI エージェント駆動開発の「足回り」に複数の欠陥・潜在リスクが顕在化した。これらは新機能の不足ではなく、既存の規約・スクリプト・手順に潜む構造的な穴であり、放置すれば各サイクルで再発・属人化を招く。

[プロダクト] v2.6.3 は新機能を追加しない patch リリースとして、7 件のバックログ Issue を 6 つの Unit で解決する。具体的には、(1) `printf -v` 系 result-out 関数の local 命名規約整備と `path-guard.sh` の予防的リファクタ、(2) `codex exec` の `</dev/null` 必須運用の SoT 明文化、(3) `operations-release.sh` への `--cycle` バリデーション導入、(4) Operations Phase マージ前 CI 通過確認フローの SoT 化、(5) `/aidlc v` 経路の再現性向上、(6) `review-flow.md` の lint 違反修正、(7) `write-history.sh` の重複ロジック共通ヘルパ化。利用者は設定変更なしで、より壊れにくい AI-DLC 環境を引き継げる。

[顧客の声] 「v2.6.2 で CI が突然落ちた原因が規約として明文化され、同じクラスのバグを書く前に気づけるようになった」「`/aidlc v` がバージョンを誤って出力することがなくなり、AI エージェントの出力を信頼できる」「マージ前の CI 修復が手順化され、サイクルごとに迷わなくなった」といった、メンテナと consumer プロジェクト双方の安心感向上が期待される。

[今後の展開] 本サイクルで整備した規約 SoT・検証手順は配布物 baseline として全 consumer プロジェクトに波及する。将来は feature 系バックログ（GitHub Projects 連携拡充、ラベル体系統一など）を minor サイクルで扱い、patch サイクルでは引き続き「振り返り由来の構造的欠陥の即時解消」を担う。

## FAQ（よくある質問）

### Q1: なぜ patch サイクルなのか？ minor ではないのか？
A: 本サイクルの 7 Issue はいずれもバグ修正・規約整備・docs・refactor・lint 修正であり、新機能追加・破壊的変更を含まない。後方互換性も維持される（`path-guard.sh` / `version.sh` / `write-history.sh` の外部インターフェース不変）。semver の patch の定義に合致するため v2.6.3 とした。

### Q2: 利用中の consumer プロジェクトに影響はあるか？
A: 破壊的変更はない。規約追記（#706 / #703）は配布物 baseline として適用されるが、既存の動作を壊すものではなく「より安全な書き方の明文化」である。スクリプト改修（#701 / #702 / #698）はいずれも外部インターフェースを変えず、既存呼び出し経路で従来と同一の結果を返すことを成功基準としている。

### Q3: 7 Issue をなぜ 6 Unit にまとめたのか？
A: Unit 001 のみ #706（result-out 関数の命名規約）と #703（codex exec の `</dev/null` 規約）を統合した。両者は既存の「AI エージェント Bash ツール経由の安全パターン」という同一テーマに属し凝集性が高いため。残り 5 Issue はそれぞれ異なる主対象ファイル・責務を持つため 1 Issue = 1 Unit とした。

### Q4: #699 はなぜ対象外なのか？
A: #699（区切り判断での AskUserQuestion 禁止ルール追加）は、現行 SKILL.md に既に該当節が存在し、Issue 本文にも「v2.6.2 Unit 002 で即時 chore コミット対応」と記載されている。実質対応済みのため本サイクルでは扱わず、別途クローズする。

### Q5: 各 Unit の実装順序に制約はあるか？
A: ない。6 Unit はすべて独立しており依存関係はない。主対象ファイルが Unit ごとに異なるため、Construction Phase では任意の順序で着手できる。優先度（High: Unit 001/002、Medium: Unit 003/004/005、Low: Unit 006）に応じた番号付けとしている。
