## DR-001: サイクルバージョンとスコープ（対象 Issue）の決定

- **ステップ**: ステップ1（セットアップ）/ ステップ2（インセプション準備）
- **日時**: 2026-05-14

### 背景

新規 Inception サイクル開始時、サイクルバージョン（patch / minor / major）と本サイクルで扱うバックログ Issue を確定する必要があった。オープン中のバックログには chore/docs/refactor/bugfix 系と feature 系が混在していた。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | v2.6.3 (patch) + chore/docs/refactor/bugfix 系 Issue を選定 | バグ修正・規約整備・保守性改善に集中。後方互換維持。リリースリスク小 | 新機能追加は次サイクルへ持ち越し |
| 2 | v2.7.0 (minor) + feature 系 Issue を含める | 新機能を今サイクルで提供できる | スコープ拡大・リリースリスク増。振り返り由来の構造的欠陥対応が後回しになる |

### 決定

**v2.6.3 (patch) + 7 Issue（#706 / #703 / #701 / #694 / #698 / #705 / #702）を選定** を採用。

### トレードオフと判断根拠

- **得たもの**: v2.6.2 振り返り・Codex レビュー指摘・実運用フィードバック由来の構造的欠陥・潜在リスクの即時解消。後方互換性の維持。小さなリリース単位
- **犠牲にしたもの**: feature 系 Issue（#700 / #685 / #666 / #664 等）の対応を次の minor サイクルへ持ち越し
- **判断根拠**: オープン中のバックログ Issue を確認した結果、patch 相当（バグ修正・規約整備・docs・refactor）の対象が 7 件あり、いずれも自己完結的で互換維持範囲。新機能の緊急性は低く、振り返り由来の欠陥を放置すると各サイクルで再発・属人化を招くため、patch サイクルでの即時解消を優先した

## DR-002: #694 の Milestone を v2.6.3 へ付け替え

- **ステップ**: ステップ5（完了処理）/ Milestone 一括紐付け
- **日時**: 2026-05-14

### 背景

`#694`（Operations マージ前 CI 通過確認フロー SoT 化）は v2.6.0 振り返り由来の Issue で、起票時に v2.6.0 Milestone に紐付けられていた。本サイクル v2.6.3 で実際に対応する（Unit 004）が、GitHub の「1 Issue = 1 Milestone」制約により、Milestone 一括紐付けスクリプトは自動付け替えせず警告のみ出力した。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | v2.6.3 に付け替え | 実際に対応するサイクルと Milestone が一致。他 6 Issue と一貫し、v2.6.3 の進捗・close が正しく追える | v2.6.0 Milestone の履歴上の紐付けが失われる |
| 2 | v2.6.0 のまま保持 | 起票時の振り返りサイクルとの紐付けが残る | 実対応サイクルと Milestone が不一致。v2.6.3 の Milestone 完了判定から漏れる |

### 決定

**v2.6.3 に付け替え** を採用。

### トレードオフと判断根拠

- **得たもの**: 本サイクルで対応する全 7 Issue が v2.6.3 Milestone に揃い、進捗管理・Operations Phase での Milestone close が正しく機能する
- **犠牲にしたもの**: v2.6.0 Milestone 上の #694 の紐付け履歴（ただし Issue 本文に「v2.6.0 振り返り由来」と明記済みのため起源は追跡可能）
- **判断根拠**: Milestone は「実際に対応するサイクル」を表すべきであり、起票起源は Issue 本文・ラベルで別途追跡できる。実対応サイクルと一致させることを優先した
