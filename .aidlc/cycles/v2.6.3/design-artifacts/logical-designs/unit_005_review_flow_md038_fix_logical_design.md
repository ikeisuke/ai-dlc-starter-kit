## 書き換えの論理パターン

### 修正前パターン（共通）

- パス列挙の説明や正規表現の説明部分で `` `, ` `` という形のコード span を埋め込み、コード span 内に
  先頭スペースまたは末尾スペースを含む状態
- markdownlint MD038/no-space-in-code に違反する

### 修正後パターン（共通）

- パスのみをコード span 化（`` `path/to/file` ``）
- 区切り文字（`,`）は平文として記述
- 半角スペースもコード span の外に出す
- 規約説明本文に「カンマ + 半角スペースで区切る」と平文で明示する

### 区切り文字を code span 化しない理由（規約意図 + 抽出側との非結合性）

1. review-summary 抽出正規表現 ``` `([^`]+)` ``` は backtick で囲まれた最短一致をパスとして取得する
2. 区切り文字（`,`）を code span 化すると、抽出側がパスではない区切り文字も取得対象としてしまい、
   新領域判定 / パス正規化に副作用を生む
3. 「区切りは平文」と統一することで、規約 / 抽出側 / 新領域判定の 3 者が以下の**明示された
   インターフェース契約**として整合する

#### 明示されたインターフェース契約

- **契約 1（`内容` 列の記法規約）**: review-summary の「内容」列には、repo-relative path のみを
  backtick で囲んだ code span として記載する。区切り文字（`,`）と半角スペースは code span 外に
  平文で配置する。複数パスは「`` `path/a` ``、平文 `,`、平文半角スペース、`` `path/b` ``」の順で
  並べる
- **契約 2（抽出正規表現 ``` `([^`]+)` ``` の適用範囲）**: 抽出側は本正規表現で backtick 内の最短
  一致のみを取得対象とする。区切り文字 `,` および半角スペースは抽出対象に含まれないことを前提と
  する
- **契約 3（新領域判定への入力）**: 新領域判定は契約 2 が返したパス集合のみを入力とする。区切り
  文字や半角スペースが入力に混入しないことを契約 1 + 契約 2 が保証する
