## DR-001: 冗長 version.txt 3 ファイルの扱い（#617）

- **ステップ**: Inception Phase ステップ1（Intent 明確化）
- **日時**: 2026-05-09

### 背景

Plugin Marketplace の `marketplace.json.metadata.version` が `2.0.4` で実体（`version.txt = 2.5.6`）と乖離しており、SoT 一本化の方針として冗長な `version.txt` 系 3 ファイル（ルート / `skills/aidlc/version.txt` / `skills/aidlc-setup/version.txt`）の扱いを決定する必要があった。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | 廃止（参照を `marketplace.json` へ移行しファイル削除） | SoT 一本化を完全達成。同期漏れが構造的に発生しなくなる | 参照側コード修正が必要、削除順序の管理が必要 |
| 2 | 自動生成（`update-version.sh` が `marketplace.json` から生成） | 後方互換維持、参照側修正不要 | ファイル多重保存と生成テスト追加が必要、SoT 二重感が残る |
| 3 | 現状維持し `update-version.sh` だけ同期拡張 | 最小侵襲、互換性最大 | SoT 二重状態が残り根本解決にならない |

### 決定

**選択肢 1（廃止）** を採用

### トレードオフと判断根拠

- **得たもの**: SoT が `marketplace.json` のみとなり、構造的に同期漏れが発生しない状態を実現
- **犠牲にしたもの**: 参照側コード（SKILL.md / 01-setup.md / env-info.sh / lib/version.sh）の移行コスト + 削除順序の慎重なオーケストレーション
- **判断根拠**: Issue #617 の根本原因は SoT 二重管理であり、選択肢 2/3 では問題が解消されない。一度のサイクルで根絶する方が長期的なメンテコスト最小化に資する

## DR-002: GitHub Projects 移行のサイクル内スコープ（#673）

- **ステップ**: Inception Phase ステップ1（Intent 明確化）
- **日時**: 2026-05-09

### 背景

GitHub Projects (ProjectsV2) 移行を v2.6.0 サイクルでどこまで実施するかを決定する必要があった。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | フル移行（Project 作成 + Item 一括投入 + #524 redirect 化 + 運用ルール更新） | v2.6.0 で完結、Inception 以降不要 | token scope 拡張作業 + Project 設計を同サイクルで実施する負荷 |
| 2 | Project 作成・スケルトンのみ（データ移行は次サイクル） | 負荷分散 | 2 サイクル跨ぎで運用変更の便益を得るのが遅れる |
| 3 | 単純調査・設計案作成のみ（POC） | 軽量、リスク最小 | 実装が他サイクルへスライド |

### 決定

**選択肢 1（フル移行）** を採用

### トレードオフと判断根拠

- **得たもの**: v2.6.0 完了時点でバックログ動的管理が稼働状態となり、次サイクルから即座に運用変更の便益を得られる
- **犠牲にしたもの**: token scope 拡張ガイド整備 + 全 Item 投入 + ドキュメント更新を本サイクル内で実施する負荷
- **判断根拠**: 運用ルール変更は分割すると手戻りが大きい。Project 設計と Item 投入は機械的作業のため、設計確定後の実装コストは見積もり可能なレンジ（5〜8h）に収まる

## DR-003: 振り返りフロー独立化の互換性方針（#667）

- **ステップ**: Inception Phase ステップ1（Intent 明確化）
- **日時**: 2026-05-09

### 背景

Operations Phase §1 の振り返りロジックを `/aidlc-retrospective` 独立スキルに移転する際、既存 Operations 内の振り返り呼び出しの後方互換をどう扱うかを決定する必要があった。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | 互換維持（Operations 内も動く / deprecation warning） | 利用者の混乱最小、段階的移行 | コードに 2 経路残存しメンテコスト増、deprecation 期間中はテスト負荷増 |
| 2 | v2.6.0 で破壊的変更（Operations 内振り返りロジック全量移転） | コードベースが clean、責務境界が明確 | minor バンプとしてはやや重い、利用者は `/aidlc r` 起動を学習する必要 |
| 3 | 設定 flag でオフ可能に（`[rules.retrospective].operations_inline = true/false`） | チームごとに選択可能 | 設定スキーマ拡張が増え、両方の経路を維持する負荷 |

### 決定

**選択肢 2（v2.6.0 で破壊的変更）** を採用

### トレードオフと判断根拠

- **得たもの**: Operations Phase §1 のコード規模が縮小し、責務境界（リリース完了 vs 振り返り）が明確化。`/aidlc r` 案内をユーザーに早期に習得してもらうことで運用変更が浸透
- **犠牲にしたもの**: 後方互換性、CHANGELOG / README / aidlc-migrate 案内整備の追加コスト
- **判断根拠**: AI-DLC は minor バンプの破壊的変更を許容する設計（CHANGELOG での明示）であり、二重経路維持の長期コストの方が高い。Operations 完了時に `/aidlc i` と並列で `/aidlc r` を案内することで利用者の学習コストを最小化

## DR-004: 本サイクルに含めるバックログ Issue の粒度

- **ステップ**: Inception Phase ステップ2（インセプション準備 / Issue 確認）
- **日時**: 2026-05-09

### 背景

v2.6.0 minor サイクルとして、Open Issue（多数）から優先度の高い 3 件 + 小バグを統合するか、3 件のみで進めるかを決定する必要があった。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | 主要 3 件のみ（#617 / #673 / #667） | サイクル規模が安定、レビュー集中 | 関連バグが残り、後続サイクルで個別対応する手間が発生 |

- **犠牲にしたもの**: サイクル規模拡大、Construction Phase の Unit 数増加（4 → 6）
- **判断根拠**: 主要 3 件と小バグの 6 件は実装で互いを阻害せず、関連 Issue を 1 サイクルで解消する方が長期的にバックログクリーンナップ速度が速い

## DR-007: Unit 003 で codex 指摘 #1（migrate-apply-config.sh パストラバーサル）の OUT_OF_SCOPE 化（Issue #680）

- **日付**: 2026-05-09
- **フェーズ**: Construction Phase / Unit 003 / コードレビュー
- **状態**: 確定

### 背景

Unit 003（marketplace.json への version SoT 一本化）のコードレビューで、codex が `skills/aidlc-migrate/scripts/migrate-apply-config.sh` の `_apply_resource()` 系（manifest 由来の `path` / `dest` を `cp` / `rm` / `mkdir -p` / `mv`）に対してパストラバーサル / 任意パス書き込みリスクを 3 round 連続で指摘した（千日手検出に該当）。Unit 003 で修正するか、別 Issue として defer するかをユーザーに確認した。

### 選択肢

| # | 選択肢 | メリット | デメリット |
|---|--------|---------|-----------|
| 1 | OUT_OF_SCOPE として Issue 起票（採用） | Unit スコープを守り計画通りリリース、修正は次サイクルで腰を据えて対応可能 | 既存セキュリティ問題が defer される（公式リポジトリ経由では発火しない理論上のリスク） |
| 2 | PENDING_MANUAL（Issue 手動起票） | Unit を計画通り完了 | 起票漏れのリスク、後続 Unit 着手時に残課題の所在が曖昧化 |
| 3 | Unit 003 で対応（スコープ拡張） | セキュリティ問題を即時解消 | 推定 4〜8 時間の追加工数、Intent 拡張が必要、影響範囲評価で他 Unit の進行が遅延 |

### 採用: 選択肢 1（OUT_OF_SCOPE + Issue 起票）

### 影響範囲

- 本サイクル v2.6.0 に migrate のセキュリティ強化は含まれない
- Issue #680 として記録、優先度 high で次サイクル対応候補
- 公式リポジトリ経由の利用では発火しない（信頼ソース前提）ため即時リスクは限定的

### トレードオフ

- **得たもの**: Unit 003 のスコープ忠実性（Intent v2.6.0「含まれるもの」非該当の項目を Unit 内で対応しない原則）、計画通りのリリース進行
- **犠牲にしたもの**: 既存パストラバーサル脆弱性の解消が次サイクルへ持ち越し
- **判断根拠**: (1) Unit 003 の境界（version SoT 一本化）に migrate のセキュリティ強化は含まれない、(2) 本 Unit が新たに導入した脆弱性ではなく v2.0 以前から存在する既存問題、(3) 修正規模が独立 Unit 相当（4〜8 時間 + クロスプラットフォーム対応 + 約 30 件のテスト影響評価）、(4) Issue #680 として記録すれば次サイクルで「migrate スクリプト全般のセキュリティハードニング」Unit として優先度付きで対応可能、(5) スコープ保護ルール上 Intent 内要件への影響なしのため automation_mode に関わらずユーザー確認は本来不要だが、Issue 起票自体が auto mode で制限されたためユーザー承認を取得
