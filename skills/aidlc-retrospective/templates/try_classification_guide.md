# Try 構造性判別ガイド（3 問固定 / v2.6.6 / #704 / Unit 002 / SC-06）

`aidlc-retrospective` skill の `steps/retrospective.md §1.2.5 Try 構造性セルフレビュー` から参照される判別ガイド。Try を T Issue 化する直前に、起草中の Try が「次回から気をつける / 個別チェック追加で済む表面的振り返り」になっていないかを 3 問固定で判別する。

本ガイドは markdown としてそのままユーザーに提示可能な形式で記述する（動的生成しない静的テンプレート）。

---

## 評価窓（共通前提）

- **評価対象**: 起草中の各 Try 1 件
- **評価窓**: 「本サイクルを含まない直前 3 サイクル分の `cycles/v*/operations/` 配下の成果物 + 同期間に作成された GitHub の `retrospective` ラベル付き Issue」を参照する。本サイクル自身の Try は他 Try との比較対象から除外する
- **評価者**: 振り返り skill 実行者（AI エージェント or 人間）。`AskUserQuestion` で必須応答を取得する

---

## 質問 1: 再発性

> この Try が解決しようとしている事象は、直近 3 サイクル分の operations 成果物 / retrospective Issue で既に同類の事象として観測されているか？

**判定指針**:

- **「観測されている」**: 同類事象が既に観測されているのに「次回から気をつける」「チェック項目を 1 つ追加する」で済ませようとしている兆候。**観点 A（気をつける逃げ）に該当する可能性が高い** → 構造改善 Try（プロセス / 規約 / SoT / CI ガード等）への昇格を検討する
- **「観測されていない」**: 本サイクル初出の事象。個別チェック追加でも初動として合理的だが、観点 B（個別 → 構造昇格）の余地を必ず検討する

**判定 input ソース**:

- `cycles/v*/operations/retrospective*.md` の Problem セクション
- GitHub `retrospective` ラベル付き Issue の Problem セクション
- `history/operations.md` の Self-Healing / フォールバック記録

---

## 質問 2: 対象レイヤ

> この Try は「心がけ / 注意喚起」のレイヤで解決しようとしているか、それとも「skill / プロンプト / SoT / CI ガード」のレイヤで構造的に解決しようとしているか？

**判定指針**:

- **「心がけ / 注意喚起」**: 「次回から気をつける」「レビュー時にチェックする」「ドキュメントに注意書きを追加する」だけで終わっている。**観点 A（気をつける逃げ）+ 観点 C（再発防止チェック逃げ）に該当** → 構造的解決（自動検出 / プロンプト改変 / SoT 化 / CI ガード追加）に昇格させる必要がある
- **「skill / プロンプト / SoT / CI ガード」**: 具体的な実装変更（`skills/*/SKILL.md` / `steps/*.md` / `config/*.toml` / `.github/workflows/*` / bash helper 等）が Try 内に含まれている。構造改善寄りで合格

**判定 input ソース**:

- Try 文言中の対象指示子（「気をつける」「注意する」「徹底する」 vs 「`skills/foo/SKILL.md` の §N に X を追記」「`.github/workflows/Y.yml` に Z を追加」等）
- 反映先候補（プロダクトリポジトリ vs AI-DLC Starter Kit upstream Issue）

## 質問 3: 再入余地

> この Try が解決しようとしている事象は、別の入り口（別の skill / 別の手順 / 別のロール）から再び踏み込まれる余地が残るか？

**判定指針**:

- **「再入余地あり」**: 例えば「Construction Phase のコードレビュー時にチェックする」と Try を立てても、同じ事象を Operations Phase のデプロイレビュー時に踏む経路が残っている。**観点 B（個別 → 構造昇格）に該当** → 再入余地のあるすべての入り口を覆う SoT or CI ガードを Try に追加する必要がある
- **「再入余地なし」**: 当該事象は 1 つの入り口からしか踏まれない構造的境界を持ち、かつその境界が **構造的根拠（SoT / 規約 / CI ガード / 単一エントリーポイント等）として Try 内で明示** されている場合に限り、個別チェック追加でも合格。「再入余地が思い付かないから合格」は本ガイドの主旨（チェック追加逃げを避ける）に反するため、根拠不明示時は観点 A 該当として差し戻し対象とする

**判定 input ソース**:

- 事象の発生位置（Phase / Step / Skill / ファイルパス）
- 同類事象が他の入り口（別 Phase / 別 Skill / 別 CI Job）で踏まれる可能性

---

## 出力の使い方

本ガイドは判別の参考情報であり、機械判定は行わない。`AskUserQuestion`（`steps/retrospective.md §1.2.5`）で 3 観点（観点 A: 気をつける逃げ / 観点 B: 個別→構造昇格 / 観点 C: 再発防止チェック逃げ）を必須確認する際、本ガイドの 3 質問への回答を内省的に行ってから AskUserQuestion に応答することを推奨する。

差し戻しループ（最大 3 回）に入った場合は本ガイドを再読し、Try を構造改善寄りに書き直す。3 回上限到達時は `selfreview-capped` ラベル付与で T Issue 起票を許可するが、これは「構造改善が困難な事象」を後追いで識別するための警告ラベルである。
